AWS DevOps -pikakurssi

Terraformilla rakennettava infrastruktuuri Python-, Django-/FastAPI-, Next.js-, PostgreSQL- ja Docker-sovelluksille.

Kurssin käyttö ja oppimistavoitteet

Tämä materiaali opettaa rakentamaan ja julkaisemaan pienen web-sovelluksen AWS:ään infrastruktuuri koodina -periaatteella. Tavoitteena ei ole opetella ulkoa kaikkia AWS-palveluita, vaan ymmärtää, miten sovelluksen osat liittyvät toisiinsa.

Kurssin jälkeen osaat

  • kuvata AWS-infrastruktuurin Terraformilla ja tarkistaa muutokset ennen niiden toteuttamista
  • erottaa verkon, sovelluksen, tietokannan ja tiedostojen tallennuksen vastuut toisistaan
  • rakentaa Docker-imagen, tallentaa sen ECR:ään ja ajaa sen ECS Fargatessa
  • hallita sovelluksen käyttöoikeuksia IAM-rooleilla ja säilyttää salaisuudet erillään lähdekoodista
  • kerätä lokit ja mittarit sekä julkaista uusi sovellusversio GitHub Actionsilla

Suositellut esitiedot

Hyödyksi ovat Gitin, komentorivin, Dockerin, HTTP:n ja tietokantojen perusteet. Python- ja Django/FastAPI-osaaminen helpottaa esimerkkien soveltamista. Kubernetesia ei tarvitse osata etukäteen.

Opiskelujärjestys

1. PerustaTerraform, IAM ja VPC: miten infrastruktuuri kuvataan, suojataan ja verkotetaan.
2. SovellusECR, Secrets Manager, RDS, ECS ja ALB: miten sovellus paketoidaan ja tuodaan käyttäjien saataville.
3. Käyttö ja ylläpitoCloudWatch, S3, DNS, sertifikaatit ja CI/CD: miten palvelua seurataan ja päivitetään.
4. Syventävät aiheetEKS, EC2, Lambda ja tapahtumapohjainen arkkitehtuuri: vaihtoehtoisia tapoja ratkaista erilaisia tarpeita.

Suositus: Tee ensin kurssin peruspolku Terraformista ECS:ään. EKS, EC2 ja event-driven-palvelut ovat täydentäviä aiheita, eivät edellytys ensimmäisen web-sovelluksen julkaisemiselle.

Työkalut ja turvallinen aloitus

Tarvitset AWS-tilin, AWS CLI:n, Terraformin (vähintään 1.10 S3:n natiivia state-lukitusta varten), Dockerin, Gitin ja GitHub-repositorion. Käytä AWS:ään kirjautumiseen ensisijaisesti väliaikaisia tunnuksia esimerkiksi IAM Identity Centerin kautta. Ota monivaiheinen tunnistautuminen käyttöön äläkä käytä root-käyttäjää päivittäiseen työhön.

Esimerkkien nimet, domainit, tilitunnisteet ja salaisuudet ovat paikkamerkkejä. Korvaa ne omilla arvoillasi. Terraform-koodikatkelmat havainnollistavat yksittäisiä resursseja; ne eivät muodosta yhtä sellaisenaan ajettavaa projektia, ellei kaikkia riippuvuuksia, muuttujia ja tiedostoja ole lisätty.

1. Johdanto ja pelisäännöt

AWS (Amazon Web Services) tarjoaa satoja pilvipalveluita. DevOps-työssä et tarvitse niitä kaikkia. Tässä kurssissa keskitytään tavallisen web-sovelluksen ympäristöön: verkkoon, tietokantaan, konttien ajamiseen, kuormantasaamiseen, tiedostoihin, DNS:ään, lokitukseen ja automaatioon.

Kolme käsitettä muodostavat AWS:n maantieteellisen ja hallinnollisen perustan:

  • Region (alue): maantieteellinen AWS-alue, esimerkiksi eu-north-1 eli Tukholma. Resurssi luodaan yleensä tiettyyn regioniin. Valintaan vaikuttavat latenssin lisäksi palveluiden saatavuus, tietojen sijaintivaatimukset ja hinta — lähin alue ei ole automaattisesti paras kaikissa tilanteissa.
  • Availability Zone (AZ, saatavuusvyöhyke): regionin sisäinen erillinen sijainti, jolla on omat infrastruktuurinsa. Käyttämällä useampaa AZ:ta voidaan parantaa vikasietoisuutta, mutta se voi myös kasvattaa kustannuksia.
  • AWS Account (tili): hallinnollinen, käyttöoikeuksiin ja laskutukseen liittyvä raja. Erilliset tilit esimerkiksi kehitykselle ja tuotannolle auttavat rajaamaan virheiden ja väärien käyttöoikeuksien vaikutuksia.

Kustannus- ja turvallisuusvaroitus

AWS voi veloittaa varatuista resursseista myös silloin, kun sovelluksella ei ole käyttäjiä. Esimerkiksi NAT Gateway, Application Load Balancer ja käynnissä oleva RDS-instanssi kerryttävät kustannuksia tyhjäkäynnilläkin. Myös tallennus, julkiset IP-osoitteet, lokit ja datasiirrot voivat maksaa erikseen.

  • Aseta laskutushälytys heti (AWS Budgets, esim. 10 €/kk).
  • Kokeile aina terraform plan ennen apply-komentoa.
  • Opettelun jälkeen aja terraform destroy, ettet jätä resursseja pyörimään.
  • Älä koskaan kirjoita avaimia koodiin tai tiedostoihin. Käytä IAM-rooleja ja Secrets Manageria.

2. Terraform-perusta

Hinnoittelu ja ilmainen taso

Terraform CLI:n käyttö ei itsessään aiheuta AWS-resurssimaksua. Kustannus syntyy esimerkiksi state-tiedoston S3-tallennuksesta ja pyynnöistä. Tässä esimerkissä käytetään S3:n omaa lukitustiedostoa, joten erillistä DynamoDB-taulua ei tarvita.

Terraform on infrastructure as code (IaC) -työkalu. Kuvaat halutun infrastruktuurin HCL-tiedostoihin. Terraform vertaa kuvausta tallennettuun tilaan (state) ja AWS:n todellisiin resursseihin, minkä perusteella se ehdottaa luotavia, muutettavia tai poistettavia resursseja.

Liittyy muihin: AWS Provider (AWS:n API-rajapintaa käyttävä lisäosa), S3 (jaettu state-tiedosto), CI/CD-putket ja IAM (Terraformin käyttöoikeudet).

Tärkeät Terraform-termit: resource luo tai hallitsee resurssia, data source lukee jo olemassa olevan tiedon, provider yhdistää Terraformin palveluun ja state pitää kirjaa Terraformin hallitsemista resursseista.

Mihin sitä käytetään ja miksi

  • Infrastruktuuri on toistettava: sama koodi tuottaa saman ympäristön kehitykseen, testiin ja tuotantoon.
  • Muutokset näkyvät versionhallinnassa ja niistä voi tehdä katselmoinnin pull requestilla.
  • Konsoliklikkailu ei skaalaudu eikä jää dokumentoiduksi. Koodi on dokumentaatio.
  • plan-vaihe näyttää etukäteen, mitä muuttuu, ja vähentää yllätyksiä.

Perusrakenne ja tilan tallennus

terraform {
  # S3:n natiivi state-lukitus on käytettävissä Terraform 1.10+:ssa.
  required_version = ">= 1.10.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0" # kurssin esimerkit on kirjoitettu AWS Provider 5.x:lle
    }
  }
  backend "s3" {
    bucket       = "YOUR-UNIQUE-TFSTATE-BUCKET"
    key          = "devops-demo/terraform.tfstate"
    region       = "eu-north-1"
    encrypt      = true
    use_lockfile = true
  }
}

provider "aws" {
  region = "eu-north-1"
  # Tagit kaikille resursseille automaattisesti (kustannusseuranta!)
  default_tags {
    tags = {
      Project   = "devops-demo"
      ManagedBy = "terraform"
    }
  }
}

Vinkki: Tila (terraform.tfstate) voi sisältää salaisuuksia ja muita arkaluontoisia arvoja. Älä koskaan committaa sitä Gitiin. Käytä S3-backendia, versionointia, julkisen käytön estoa ja tarkasti rajattuja IAM-oikeuksia.

Backend pitää alustaa ensin: S3-bucketin täytyy olla olemassa ennen kuin Terraform voi tallentaa state-tiedoston siihen. Luo backend-bucket erillisellä pienellä bootstrap-konfiguraatiolla tai AWS-konsolissa. Ota bucketin versionointi ja julkisen käytön esto käyttöön. Lisää tämän jälkeen S3-backend yllä olevaan konfiguraatioon ja suorita terraform init -migrate-state, jos siirrät aiemmin paikallisesti tallennetun tilan.

Esimerkki käyttää S3:n omaa use_lockfile-lukitusta. Vanha DynamoDB-lukitus on HashiCorpin nykyisessä S3-backend-dokumentaatiossa vanhentuvaksi merkitty vaihtoehto.

Esimerkki: backend-bucketin bootstrap

Seuraava pieni konfiguraatio ajetaan ensin erillisessä hakemistossa paikallisella state-tiedostolla. Lisää tähän lisäksi bucketin nimen yksilöllisyys ja käyttöoikeudet organisaatiosi tarpeiden mukaan.

resource "aws_s3_bucket" "tfstate" {
  bucket = "YOUR-UNIQUE-TFSTATE-BUCKET"
}

resource "aws_s3_bucket_versioning" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "tfstate" {
  bucket                  = aws_s3_bucket.tfstate.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"

Kun bucket on luotu, siirry varsinaiseen infrastruktuuriprojektiin, määritä sen S3-backend ja suorita terraform init -migrate-state. Säilytä bootstrap-projektin state turvallisesti; se hallitsee backend-bucketia itseään.

3. IAM (Identity and Access Management)

Hinnoittelu ja ilmainen taso

IAM-käyttäjät, roolit, ryhmät ja politiikat ovat ilmaisia. Maksu tulee vain palveluista, joita roolit käyttävät.

Mitä se on: IAM määrittää, kuka tai mikä saa tehdä mitä AWS:ssä. Policy eli käyttöoikeuspolitiikka määrittelee sallitut ja kielletyt toiminnot. Role eli rooli on identiteetti, jonka palvelu tai käyttäjä voi ottaa käyttöön väliaikaisia tunnuksia vastaan. Trust policy määrittelee, kuka saa ottaa roolin; tavallinen permissions policy määrittelee, mitä roolin haltija saa tehdä.

Liittyy muihin: kaikki AWS-palvelut. ECS:n suoritusrooli hakee imaget ja salaisuudet sekä kirjoittaa lokit, sovelluksen task role antaa sovelluskoodille sen tarvitsemat AWS-oikeudet ja GitHub Actions ottaa käyttöön rajatun deploy-roolin OIDC:n avulla.

Mihin sitä käytetään ja miksi

  • Vähimmän oikeuden periaate: jokainen palvelu saa vain ne oikeudet, joita se tarvitsee. Jos sovellus vuotaa, vahinko rajoittuu.
  • Roolit palveluille: ECS-tehtävä ei tarvitse käyttäjätunnusta. Se ottaa roolin ja saa väliaikaiset tunnukset.
  • Ei pitkäaikaisia avaimia: roolit ja OIDC poistavat tarpeen tallentaa AWS-avaimia CI-palveluun.

Esimerkki: palveluroolin luominen

data "aws_iam_policy_document" "ecs_assume" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ecs-tasks.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "ecs_execution" {
  name               = "demo-ecs-execution"
  assume_role_policy = data.aws_iam_policy_document.ecs_assume.json
}

# AWS:n valmis politiikka: kuvien veto ECR:stä ja lokien kirjoitus
resource "aws_iam_role_policy_attachment" "ecs_execution" {
  role       = aws_iam_role.ecs_execution.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

Vältä "Action": "*" ja "Resource": "*" -yhdistelmää. Se on käytännössä admin-oikeus, ja se on yleisin syy vuotoihin.

4. VPC ja verkko

Hinnoittelu ja ilmainen taso

KomponenttiHinta
VPC, aliverkot, reititystaulut, IGW, Security GroupitIlmaisia
NAT Gateway0,045 $/h (≈ 32,85 $/kk) + 0,045 $/GB, per AZ
Julkinen IPv40,005 $/h (≈ 3,65 $/kk) per osoite

NAT on yleisin piilokulu. Yhden NAT:in pitäminen päällä kuukauden ajan maksaa enemmän kuin koko kurssiesimerkin muu infra.

Mitä se on: VPC (Virtual Private Cloud) on AWS-tilisi loogisesti eristetty IP-verkko. Sen sisällä on aliverkkoja (subnet), reititystauluja, Internet Gateway (IGW) ja tarvittaessa NAT Gateway. Security Group on tilallinen palomuuri, joka säätelee resurssien verkkoliikennettä.

Liittyy muihin: lähes kaikki verkkoa käyttävät palvelut: RDS, ECS, ALB, EC2 ja VPC:hen liitetty Lambda.

Julkinen vs. yksityinen aliverkko: julkisella aliverkolla on reitti Internet Gatewaylle. Yksityisellä aliverkolla ei ole suoraa reittiä internetiin. NAT Gateway mahdollistaa yksityisestä aliverkosta lähtevän internetliikenteen, mutta ei avaa sinne suoria yhteyksiä internetistä. Security Group rajaa vielä erikseen, mitkä yhteydet sallitaan.

Mihin sitä käytetään ja miksi

  • Julkinen ja yksityinen eristys: tavallisesti ALB on julkisessa aliverkossa ja tietokanta sekä sovelluskontit yksityisissä aliverkoissa. Kurssin myöhempi ECS-esimerkki käyttää oppimisen ja kustannusten havainnollistamiseksi julkista aliverkkoa sovellustehtäville; tuotannossa tehtävät siirretään yleensä yksityisiin aliverkkoihin.
  • Usean AZ:n redundanssi: kaksi aliverkkoa eri AZ:issa, jotta yksi datakeskuksen vika ei kaada palvelua.
  • Security Groupit: sallitaan vain tarvittava liikenne, esim. ALB → sovellus porttiin 8000, sovellus → tietokanta porttiin 5432.

5. ECR (Elastic Container Registry)

Hinnoittelu ja ilmainen taso

Tallennus noin 0,10 $ / GB / kk. Pieni Django- tai FastAPI-image on noin 100–300 MB, joten kustannus on muutama sentti kuukaudessa. Elinkaarisääntö pitää vanhat imaget pois. Siirrot samaan regioniin ECS:ään eivät aiheuta siirtomaksua.

Mitä se on: AWS:n yksityinen konttirekisteri. Tallennat siihen rakennetun Docker-imagen, jonka ECS, Lambda tai EKS voi hakea ajoa varten. Rekisteri ei aja sovellusta — se säilyttää versioidut imaget.

Liittyy muihin: Docker (imagen rakentaminen), ECS/Lambda/EKS (imagen suorittaminen), GitHub Actions (julkaisu) ja IAM (pääsy rekisteriin).

Image ja tag: image on sovelluksesta ja sen riippuvuuksista rakennettu paketti. Tag, kuten Git-commitin tunniste, kertoo mistä koodiversiosta image on rakennettu. Muuttumaton tagi auttaa varmistamaan, että tuotantoon julkaistu versio voidaan tunnistaa jälkikäteen.

Mihin sitä käytetään ja miksi

  • Imagen versiointi: jokainen build saa tagin (esim. git-commit-hash), jolloin tiedät tarkalleen mikä koodi on tuotannossa.
  • Turvallisuus: automaattinen haavoittuvuusskannaus (scan_on_push) kertoo riippuvuuksien ongelmista.
  • Lähellä kuormaa: saman alueen sisällä imagen veto on nopeaa eikä vie internet-kaistaa.

Esimerkki

resource "aws_ecr_repository" "app" {
  name                 = "devops-demo"
  image_tag_mutability = "IMMUTABLE"   # sama tagi ei voi ylikirjoittua

  image_scanning_configuration {
    scan_on_push = true
  }
}

# Elinkaarisääntö: pidetään vain 10 viimeisintä imagea, jotta tila ei kasva
resource "aws_ecr_lifecycle_policy" "app" {
  repository = aws_ecr_repository.app.name
  policy = jsonencode({
    rules = [{
      rulePriority = 1
      description  = "Pidä 10 viimeisintä"
      selection = {
        tagStatus   = "any"
        countType   = "imageCountMoreThan"
        countNumber = 10
      }
      action = { type = "expire" }
    }]
  })
}

Docker-kuvan rakentaminen ja työntäminen: aws ecr get-login-password --region eu-north-1 | docker login --username AWS --password-stdin <tili>.dkr.ecr.eu-north-1.amazonaws.com, sitten docker build -t devops-demo . ja docker push.

8. ECS Fargate (Docker-kontit ilman palvelimia)

Hinnoittelu ja ilmainen taso

Tehtävän kokoHinta / tuntiHinta / kk
0,25 vCPU / 0,5 GB0,0123 $≈ 9 $
0,5 vCPU / 1 GB0,0247 $≈ 18 $

ECS-klusteri ja palvelu ovat ilmaisia, eikä niillä ole hallintamaksua. EKS maksaa 0,10 $/h klusterista, eli noin 73 $/kk. Fargate-tehtävät laskutetaan allokoidun vCPU:n ja muistin mukaan, ei käytön mukaan. Jos tehtävä on 1 vCPU mutta käyttää 15 % siitä, maksat silti täyden hinnan.

Kurssin esimerkissä jokainen tehtävä saa julkisen IP:n (assign_public_ip = true), joten kahden tehtävän lisäksi tulee 2 × 3,65 $/kk. Tuotannossa NAT vaihtaa tämän toiseen maksuun, joten laske molemmat.

Mitä se on: ECS (Elastic Container Service) hallitsee konttien ajamista. Fargate-tilassa et ylläpidä EC2-palvelimia: määrittelet tehtävän tarvitsemat CPU- ja muistiresurssit sekä halutun tehtävämäärän, ja AWS huolehtii ajoinfrastruktuurista.

Liittyy muihin: ECR (imaget), ALB (sisääntuleva liikenne), CloudWatch (lokit), IAM (execution role ja task role), Secrets Manager, VPC ja RDS.

Kolme ECS-käsitettä: Task definition kuvaa, mitä kontteja ja asetuksia tehtävä sisältää. Task on tämän määrittelyn perusteella käynnissä oleva instanssi. Service pitää yllä haluttua task-määrää ja käynnistää korvaavan tehtävän, jos jokin pysähtyy.

Mihin sitä käytetään ja miksi

  • Sovelluksen ajo konteissa: sama Docker-image toimii kehityksessä ja tuotannossa, ja kontit voi ajaa useana kopiona.
  • Automaattinen palautuminen: ECS käynnistää kuolleen kontin uudelleen ja ylläpitää haluttua määrää (desired_count).
  • Rolling deploy: uusi versio käynnistyy vanhan rinnalle, ja liikenne siirtyy vasta terveenä. Virheen sattuessa vanha versio pysyy.
  • Ei palvelinhallintaa: ei käyttöjärjestelmäpäivityksiä, ei kapasiteettisuunnittelua.

9. EKS (Elastic Kubernetes Service) — syventävä aihe

Mitä se on: EKS on AWS:n hallinnoima Kubernetes. AWS ylläpitää Kubernetesin control planea (API-palvelin, etcd, scheduler), ja sinä hallitset worker-solmuja tai Fargate-podeja sekä kaikkea, mikä ajetaan klusterissa. Kubernetes on ECS:ää laajempi ja monimutkaisempi alusta, mutta se on myös standardi, joka toimii samalla tavalla pilvestä toiseen.

Liittyy muihin: ECR (imagen säilytys), ALB Ingress Controller tai AWS Load Balancer Controller (ALB:n luonti Ingressistä), EBS ja EFS (tallennus), IAM Roles for Service Accounts tai EKS Pod Identity (oikeudet podeille), Karpenter ja Cluster Autoscaler (solmujen skaalaus), CloudWatch Container Insights ja Prometheus/Grafana (havainnointi), Helm ja Argo CD (sovellusten asennus ja GitOps).

Mihin sitä käytetään ja miksi

  • Monipalveluinen järjestelmä: kun palveluita on kymmeniä ja niiden välillä on monimutkaisia riippuvuuksia, Kubernetesin deklaratiivinen malli (haluttu tila YAML:ssä, klusteri pitää sen yllä) pitää kokonaisuuden hallittavana.
  • Siirrettävyys: Kubernetes-manifestit toimivat samoin EKS:ssä, GKE:ssa, AKS:ssa ja omalla palvelimella. Tämä on tärkeää, jos haluat välttää lukkiutumisen yhteen pilveen.
  • Itseparantuminen ja rullaavat päivitykset: Deployment korvaa kuolleet podit, ja readiness-probe estää liikenteen rikkinäisiin versioihin. Canary-julkaisut onnistuvat Argo Rollouts -työkalulla.
  • Ekosysteemi: Helm-kaaviot, Operaattorit ja valmiit monitorointipinot (esim. Prometheus) löytyvät suoraan, eikä niitä tarvitse kirjoittaa itse.
  • Oppiminen: Kubernetes-osaaminen on työmarkkinoilla yleisesti haettu taito. Jos käytät jo K3s:ää kotipalvelimella, käsitteet (Pod, Deployment, Service, Ingress, ConfigMap, Secret) siirtyvät EKS:ään suoraan.

Milloin EKS ei kannata

  • Yksi tai kaksi palvelua: ECS Fargate on yksinkertaisempi ja usein halvempi, koska klusterin ylläpito jää pois.
  • Pieni tiimi ilman platform-osaamista: EKS:n päivitykset (Kubernetes-versiot tulevat noin kolmen kuukauden välein ja vanhenevat), add-onit, verkkoasetukset ja IAM-yhdistäminen vaativat jatkuvaa huomiota.
  • Serverless-kuormat: Lambda tai Step Functions sopivat paremmin lyhyisiin ja tapahtumapohjaisiin tehtäviin.

Hinnoittelu ja ilmainen taso

KomponenttiHinta (suuntaa antava)
EKS control plane0,10 $/h per klusteri ≈ 73 $/kk. Ei ilmaista tasoa.
Worker-solmut EC2:ssaNormaali EC2-hinta solmun koon mukaan. Yksi t3.medium on noin 30 $/kk.
Fargate-poditSamat hinnat kuin ECS Fargatessa, ks. aiempi osio
Load balancer, NAT, EBS, IP-osoitteetSamat hinnat kuin muissa palveluissa, ja ne kertyvät helposti

Pienin järkevä EKS-kokoonpano (kaksi solmua, yksi klusteri, ALB ja NAT) maksaa helposti 200–250 $/kk ennen sovelluskuormaa. Tämä on tärkein syy valita ECS, jos palveluita on vähän.

Oppimisvinkki: Ennen EKS:ää opettele K3s tai kind paikallisesti. Samat kubectl-komennot ja manifestit toimivat, joten opit käsitteet ilman pilvilaskua.

Hinnoittelu ja ilmainen taso

Mitä se on: ALB on HTTP-tason kuormantasaaja. Se vastaanottaa käyttäjien yhteydet ja välittää pyynnöt terveiksi todetuille kohteille (target group). Se voi myös päättää TLS-yhteyden ja reitittää pyyntöjä esimerkiksi URL-polun perusteella.

Liittyy muihin: ECS (kohdepalvelut), ACM (TLS-sertifikaatti), Route 53 (DNS), Security Groups ja CloudWatch.

Esimerkki polkureitityksestä: yksi ALB voi ohjata polun /api/* Django/FastAPI-kohderyhmään ja muut pyynnöt Next.js-kohderyhmään. Jokaiselle sovelluspalvelulle määritellään tällöin oma target group ja sopiva health check.

Mihin sitä käytetään ja miksi

  • Terveyden tarkistus: ALB poistaa kontit, jotka eivät vastaa /health/-polkuun, joten rikkinäinen versio ei saa liikennettä.
  • Nollakatkoinen deploy: uusi ECS-tehtävä rekisteröityy kohderyhmään vasta, kun se on terve.
  • TLS-päätepiste: sertifikaatti on ALB:llä, sovellus voi puhua HTTP:tä sisäverkossa.
  • Polkureititys: yksi domain, useita palveluita (monoliitti vs. API + frontend).

13. CloudFront (CDN)

Hinnoittelu ja ilmainen taso

CloudFront laskuttaa siirrosta ja pyynnöistä. Siirto internetiin on noin 0,085–0,09 $/GB (alueesta riippuen). CloudFrontin aina-ilmaisen tason suuruus vaihtelee ajan myötä, joten tarkista sen nykyinen määrä AWS:n Free Tier -sivulta ennen käyttöönottoa. Pieni staattinen sivusto jää yleensä muutaman dollarin kuukausikustannukseen.

Mitä se on: CloudFront on sisältöjakeluverkko (CDN). Se voi välimuistittaa sisältöä käyttäjän lähellä sijaitsevissa reunapalvelupisteissä ja vähentää alkuperäpalvelimelle tulevia pyyntöjä. ACM-sertifikaatin hallinta ei maksa erikseen, mutta CloudFrontin liikenteestä ja pyynnöistä voidaan veloittaa.

Liittyy muihin: S3 (staattisen sisällön alkuperä), ALB (dynaamisen sovelluksen alkuperä), ACM (CloudFrontin sertifikaatti alueella us-east-1), Route 53 ja WAF.

Mihin sitä käytetään ja miksi

  • Nopeus: Next.js-staattiset sivut ja kuvat tarjoillaan lähimmästä pisteestä Suomessa.
  • Alkuperän suojaus: Origin Access Control (OAC) sallii CloudFrontin lukea S3:a, mutta ei julkista pääsyä bucketiin.
  • Kuorman vähennys: välimuistissa olevat pyynnöt eivät osu sovellukseen tai tietokantaan.

17. CI/CD: GitHub Actions ja OIDC

Hinnoittelu ja ilmainen taso

OIDC-palveluntarjoaja ja IAM-rooli ovat ilmaisia. Kustannus syntyy vain siitä, mitä putki käyttää: ECR-tallennus, ECS-tehtävät, Fargate-ajoaika ja mahdollinen Build-kesto. Mitä se on: CI/CD-putki automatisoi muutosten tarkistamisen, testaamisen, paketoinnin ja julkaisemisen. GitHub Actions voi pyytää AWS:ltä lyhytikäiset tunnukset OIDC:n avulla, jolloin pitkäaikaisia AWS-avaimia ei tallenneta GitHubin salaisuuksiin.

  • Turvallisuus: rooli rajataan vain tiettyyn repositorioon ja haaraan.

Workflow-tiedosto GitHubissa

name: deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write    # tarvitaan OIDC-tokeniin
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: eu-north-1

      - name: Kirjaudu ECR:ään
        id: ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Rakenna ja työnnä yksilöllinen image
        env:
          REGISTRY: ${{ steps.ecr.outputs.registry }}
          TAG: ${{ github.sha }}-${{ github.run_attempt }}
        run: |
          docker build -t $REGISTRY/devops-demo:$TAG .
          docker push $REGISTRY/devops-demo:$TAG

      - name: Rekisteröi uusi task definition ja päivitä palvelu
        env:
          TASK_FAMILY: devops-demo
          CONTAINER_NAME: app
          IMAGE_URI: ${{ steps.ecr.outputs.registry }}/devops-demo:${{ github.sha }}-${{ github.run_attempt }}
        run: |
          TASK_DEF=$(aws ecs describe-task-definition \
            --task-definition "$TASK_FAMILY" \
            --query taskDefinition)

          NEW_TASK_DEF=$(echo "$TASK_DEF" | jq \
            --arg IMAGE "$IMAGE_URI" \
            --arg NAME "$CONTAINER_NAME" '
              .containerDefinitions |= map(
                if .name == $NAME then .image = $IMAGE else . end
              )
              | del(.taskDefinitionArn, .revision, .status,
                    .requiresAttributes, .compatibilities,
                    .registeredAt, .registeredBy, .deregisteredAt)
            ')

          NEW_TASK_ARN=$(aws ecs register-task-definition \
            --cli-input-json "$NEW_TASK_DEF" \
            --query 'taskDefinition.taskDefinitionArn' \
            --output text)

          aws ecs update-service \
            --cluster demo-cluster \
            --service devops-demo \
            --task-definition "$NEW_TASK_ARN"

Tässä repositorio käyttää ECR:n IMMUTABLE-asetusta ja GitHub-commitin SHA:ta sekä ajon yritysnumeroa image-tagina. Yritysnumero tekee myös saman workflow-ajon uudelleenyrityksestä uuden tagin, koska muuttumatonta ECR-tagia ei voi ylikirjoittaa. Julkaisu rekisteröi uuden ECS task definition -revisionin, joka viittaa uuteen imageen. Pelkkä --force-new-deployment ei päivitä task definitioniin kirjoitettua tagia.

Terraformin ja CI/CD:n vastuunjako: ECS-palvelun ignore_changes = [task_definition] estää Terraformia palauttamasta palvelua vanhaan task definition -versioon seuraavassa ajossa. Samalla se tarkoittaa, ettei Terraformin task definition -muutosta oteta automaattisesti käyttöön palvelussa. Sovi siis, että julkaisuputki vastaa task definition -revisionin rekisteröinnistä ja käyttöönotosta, ja testaa Terraform-muutosten sekä sovellusjulkaisujen yhteistoiminta.

Työnkulku tarvitsee IAM-roolille ECR-kuvan julkaisuun ja ECS task definitionin rekisteröintiin sekä palvelun päivittämiseen riittävät oikeudet. Se tarvitsee myös rajatun iam:PassRole-oikeuden niihin ECS-tehtävän rooleihin, joita task definition käyttää. OIDC:n trust policy kertoo, kuka saa roolin ottaa; se ei yksin anna näitä käyttöoikeuksia.

18. Event-driven -palikat

Periaate: Event-driven-arkkitehtuurissa palvelut eivät kutsu toisiaan suoraan. Ne julkaisevat tapahtuman (esim. "tilaus luotu", "tiedosto ladattu") ja muut palvelut reagoivat siihen omassa tahdissaan. Tämä irrottaa palvelut toisistaan: tuottaja ei tiedä, kuka kuuntelee, ja kuluttaja voi olla hetkellisesti alhaalla ilman, että tuottaja kaatuu.

Tyypillinen ketju:

Tuottaja (API, S3, IoT, aikataulu)
        ↓ tapahtuma
EventBridge / SNS   (reititys ja monistus)
        ↓
SQS-jono            (puskuri, uudelleenyritykset)
        ↓
Lambda / ECS-työntekijä (käsittely)
        ↓
DynamoDB / RDS / S3 (tulos)
        ↓ virheet
Dead-letter-jono    (käsittelemättömät viestit talteen)

Amazon EventBridge

Mitä se on: Tapahtumaväylä, joka vastaanottaa JSON-tapahtumia, suodattaa ne sääntöjen perusteella ja toimittaa kohteisiin (Lambda, SQS, SNS, Step Functions, ECS-tehtävä ja yli 20 muuta kohdetyyppiä). Sisältää myös Scheduler-palvelun (cron-ajastukset) ja Pipes-palvelun (lähteestä kohteeseen suodatuksen ja muunnoksen kanssa, ilman koodia).

Liittyy muihin: lähes kaikki AWS-palvelut julkaisevat tapahtumia EventBridgeen (EC2:n tilamuutokset, CodePipeline, S3, CloudTrail). Lisäksi omat sovellukset voivat julkaista omia tapahtumia "custom bus" -väylään.

Ratkaisee: reititys ilman, että tuottaja tuntee kuluttajat. Esim. sama "tilaus luotu" -tapahtuma menee laskutukseen, varastoon ja sähköpostiin, ja uusi kuluttaja lisätään vain uudella säännöllä. Myös ajastetut tehtävät ja SaaS-tapahtumien (kuten kumppanijärjestelmän webhookit) vastaanotto.

Hinta (suuntaa antava): AWS:n omat tapahtumat oletusväylällä ovat ilmaisia. Oma väylä maksaa noin 1 $ miljoonasta tapahtumasta. Scheduler sisältää ilmaisia ajoja kuukaudessa, sen jälkeen maksu per ajo.

Amazon SNS (Simple Notification Service)

Mitä se on: Pub/sub-aihe (topic), johon julkaistaan viesti ja joka monistaa sen kaikille tilaajille: SQS-jonoille, Lambdalle, HTTP-päätepisteille, sähköpostille, SMS:lle ja mobiilipushille.

Liittyy muihin: SQS (usein SNS → useita SQS-jonoja -yhdistelmä, "fan-out"), CloudWatch-hälytykset (ilmoitukset), Lambda, EventBridge (EventBridgen kohteena SNS on yleinen).

Ratkaisee: yhden tapahtuman lähettäminen usealle kuluttajalle samanaikaisesti. Esim. kuvan lataus S3:een voi laukaista thumbnail-generoinnin ja virustarkistuksen samalla kertaa. Sekä ops-ilmoitukset: hälytys menee sähköpostiin, Slackiin ja tiimin pagerille.

Hinta (suuntaa antava): noin miljoona julkaisua ilmaisia per kuukausi, sen jälkeen noin 0,50 $ per miljoona.

Amazon SQS (Simple Queue Service)

Mitä se on: Viestijono, johon tuottaja kirjoittaa ja josta kuluttaja lukee viestejä omaan tahtiinsa. Viesti poistetaan jonosta vasta, kun kuluttaja kuittaa sen käsitellyksi. Standard-jono tarjoaa vähintään kerran -toimituksen, joten sama viesti voi tulla käsiteltäväksi uudelleen. FIFO-jono säilyttää viestiryhmän järjestyksen ja tukee lähetysten deduplikointia, mutta sovelluksen on silti varauduttava uudelleenyrityksiin ja tehtävä käsittelystä idempotenttia.

Liittyy muihin: Lambda (event source mapping, joka lukee jonoa automaattisesti), SNS (fan-out), ECS-työntekijät (jonon pituuteen perustuva skaalaus), Dead-letter-jono, EventBridge Pipes.

Tärkeitä asetuksia:

  • Visibility timeout: aika, jonka viesti on piilossa muilta käsittelyn ajan. Jos käsittely kestää pidempään kuin tämä, viesti ilmestyy takaisin jonoon ja käsitellään uudelleen.
  • Dead-letter-jono (DLQ): viestit, jotka epäonnistuvat esimerkiksi viidesti peräkkäin, siirretään erilliseen jonoon. Näin yksi rikkinäinen viesti ei jumita koko jonoa, ja virheen voi tutkia myöhemmin.
  • Long polling: kuluttaja odottaa viestejä yhteyden päässä, jolloin tyhjät vastaukset ja pyyntökulut vähenevät.

Ratkaisee: kuormanpuskurointi (piikit eivät kaada tietokantaa), palveluiden irrotus, uudelleenyritykset ja se, että työntekijä voi olla hetken alhaalla ilman datan katoamista.

Hinta (suuntaa antava): ensimmäiset miljoona pyyntöä kuukaudessa ilmaisia aina. Sen jälkeen noin 0,40 $ per miljoona pyyntöä Standard-jonossa. Käytännössä jonot ovat yleensä hyvin halpoja.

Lambda-tapahtumalähteet

Mitä se on: Lambdalla on useita tapoja saada tapahtumia: suora kutsu (synkroninen, esim. API Gatewayn kautta), asynkroninen kutsu (esim. S3-ilmoitus, EventBridge-sääntö) ja event source mapping, joka lukee SQS-, Kinesis-, DynamoDB Streams- tai MSK-lähteitä ja toimittaa niistä eriä (batch) funktiolle.

Liittyy muihin: SQS, Kinesis, DynamoDB Streams, S3-tapahtumat, EventBridge, API Gateway.

Ratkaisee: Lambdalle ei tarvitse kirjoittaa pollausluuppia. Lambda skaalautuu lähteen mukaan, ja virheelliset erät voidaan ohjata DLQ:hun tai bisect-toiminnolla pienempiin osiin.

Hinta: Lambda-hinta (pyynnöt ja GB-sekunnit) per käsittely, sekä lähteen oma hinta (SQS, Kinesis jne.). Aina-ilmaista tasoa ks. Lambda-osio.

Amazon Kinesis Data Streams ja Data Firehose

Mitä se on: Kinesis Data Streams on suoratoistopalvelu, jossa tapahtumat ovat järjestettyjä shardeihin ja säilyvät streamissä (oletuksena 24 h, enintään 365 pv). Monta kuluttajaa voi lukea samaa dataa itsenäisesti. Firehose on "kuljeta ja tallenna" -palvelu, joka kirjoittaa striimin S3:een, Redshiftiin tai OpenSearchiin ilman omaa koodia, usein Parquet-muodossa.

Liittyy muihin: Lambda (striimin kuluttajana), Glue ja Athena (datan kysely S3:sta), S3 (data lake), Managed Service for Apache Flink (reaaliaikainen käsittely), CloudWatch.

Ratkaisee: suuren määrän laitedataa, klikkausvirtoja tai lokeja reaaliajassa. Tyypillinen data engineering -malli: Kinesis → Firehose → S3 Parquet → Athena. Myös se, että useat kuluttajat tarvitsevat samaa dataa eri tahtiin.

Hinta (suuntaa antava): Data Streams maksaa shardeista (noin 11 $/kk per shard provisioned-tilassa, lisäksi siirrot). Firehose maksaa per ingestoitu GB, noin 0,03 $/GB. Kinesis ei ole ilmainen, joten kokeilun jälkeen sammuta se.

Amazon MSK (Managed Streaming for Apache Kafka)

Mitä se on: Hallittu Apache Kafka -klusteri. Kafka on suosittu, mutta operoinnissaan raskas, ja MSK ottaa brokerit, päivitykset ja replikoinnin hoitaakseen. Ohjelmointirajapinta on sama kuin avoimessa Kafkassa, joten kaikki Kafka-työkalut ja -kirjastot toimivat.

Liittyy muihin: Lambda (MSK event source mapping), Kafka Connect (esim. tietokantamuutosten striimaus), MSK Connect, Glue Schema Registry, Flink.

Ratkaisee: kun tarvitset Kafkan semantiikkaa (pitkä säilytys, kompaktointi, avain-pohjainen järjestys, laaja ekosysteemi) tai tiimi jo osaa Kafkan. Muuten Kinesis tai SQS on yleensä yksinkertaisempi.

Hinta (suuntaa antava): maksat brokereista tunneittain, vähintään kaksi tai kolme brokeria. Pienikin klusteri maksaa usein useita satoja dollareita kuukaudessa. Tämä tekee MSK:sta kalliin kehitykseen. Serverless-versio on olemassa, mutta sekin on kalliimpi kuin pienet SQS-jonot.

AWS Step Functions

Mitä se on: Tilakone (state machine), joka orkestroi useita vaiheita: Lambdoja, ECS-tehtäviä, API-kutsuja ja muita palveluita. Määritys on JSON tai YAML (Amazon States Language), ja siinä on valmiit uudelleenyritykset, haarautumiset, rinnakkaisajo ja virheenkäsittely.

Liittyy muihin: Lambda, ECS, EventBridge (käynnistys), SQS ja SNS, DynamoDB, Glue-työt, Athena.

Ratkaisee: monivaiheiset prosessit, joissa pitää tietää missä vaiheessa mennään. Esim. tilauksen käsittely: maksu → varastovaraus → toimitus → ilmoitus, ja jos maksu epäonnistuu, kompensoiva toiminta ajetaan. Ilman tätä logiikka päätyy koodiin, joka on vaikea jäljittää.

Hinta (suuntaa antava): Standard-tilassa noin 0,025 $ tuhatta tilasiirtymää kohden. Ilmaisia siirtymiä on 4 000 kuukaudessa aina. Express-tila on halvempi suurelle, lyhytkestoiselle kuormalle.

Amazon EventBridge Pipes

Mitä se on: Putki lähteen ja kohteen välillä. Esimerkiksi DynamoDB Streams → suodatus → Step Functions tai SQS → muunnos → EventBridge-väylä ilman erillistä välikoodia.

Ratkaisee: yksinkertaiset integraatiot, joissa halutaan vain suodatus ja muunnos. Jos logiikkaa on paljon, Lambda on parempi.

DynamoDB Streams ja S3-tapahtumailmoitukset

Mitä ne ovat: DynamoDB Streams julkaisee taulun muutokset (lisäys, muokkaus, poisto) järjestyksessä. S3-tapahtumat kertovat, kun objekti luodaan tai poistetaan, ja ne voivat kohdistua Lambdaan, SQS:ään, SNS:ään tai EventBridgeen.

Liittyy muihin: Lambda, EventBridge, Kinesis (DynamoDB Streamsin voi kytkeä Kinesisiin), OpenSearch (indeksointi muutoksista).

Ratkaisee: välimuistin päivitys, hakuindeksin ylläpito, muutosloki ja tiedoston käsittely heti latauksen jälkeen. Muutokset tulevat ilman, että sovellus kertoo niistä erikseen (eikä tarvitse muistaa kirjoittaa kahteen paikkaan).

Hinta: DynamoDB Streams ei maksa erikseen, mutta lukuja laskutetaan normaalisti. S3-tapahtumista maksetaan kohteen (Lambda, SQS jne.) hinta.

Mitä event-driven-järjestelmässä pitää muistaa

  • Vähintään kerran -toimitus: useimmat palvelut voivat toimittaa saman viestin kahdesti. Käsittelijän on oltava idempotentti, eli kahdesti ajettuna lopputulos on sama. Käytä yksilöllistä viestitunnusta tarkistukseen.
  • Järjestys: Standard-jonot eivät takaa järjestystä. Jos käsittelyjärjestys on liiketoimintalogiikan kannalta tärkeä, käytä FIFO-jonoa tai järjestettyä stream-ratkaisua.
  • Dead-letter-jono (DLQ): määritä uudelleenyritysten rajat ja DLQ etenkin tuotantokäytössä. DLQ säilyttää viestit, joita ei saada käsiteltyä, jotta syy voidaan tutkia ja viestit voidaan käsitellä hallitusti uudelleen. Seuraa DLQ:n viestimäärää CloudWatch-hälytyksellä.
  • Outbox-malli: jos tietokantaan kirjoittaminen ja tapahtuman julkaisu pitää onnistua yhdessä, kirjoita tapahtuma samaan transaktioon outbox-tauluun, ja erillinen prosessi julkaisee sen. Näin tapahtuma ei katoa, jos julkaisu epäonnistuu.
  • Tapahtuman muoto: versioi skeema ja lisää tapahtumaan aikaleima ja tunniste. Muuten muutos tuottajassa rikkoo kuluttajat hiljaa.
  • Havainnointi: jokainen tapahtuma tarvitsee korrelaatio-ID:n, jotta ketjun voi seurata lokeista (X-Ray tai OpenTelemetry).

19. Kokoava harjoitus

Rakenna pieni Django- tai FastAPI-sovellus ja julkaise se AWS:ään. Tee kokonaisuus vaiheittain: tarkista jokaisen vaiheen toiminta ennen seuraavan lisäämistä.

  1. Projektin perusta: luo Terraform-projekti, provider ja turvallinen S3-backend. Varmista, että terraform init, validate ja plan toimivat.
  2. Verkko: luo VPC, kaksi julkista aliverkkoa ALB:lle, yksityiset aliverkot RDS:lle ja Security Groupit, jotka sallivat vain tarvittavat yhteydet.
  3. Sovelluksen paketoiminen: rakenna Docker-image, luo ECR-repositorio ja julkaise image yksilöllisellä tagilla.
  4. Tietokanta ja salaisuudet: luo RDS PostgreSQL yksityiseen aliverkkoon, ota salasanan hallinta Secrets Manageriin ja varmista, että sovellus saa yhteyden tietokantaan.
  5. Sovelluksen ajaminen: luo ECS Fargate -task definition ja service, ALB sekä CloudWatch-lokiryhmä. Aloita yhdellä taskilla, lisää toinen vasta kun perusversio toimii.
  6. Havainnointi: toteuta sovellukseen toimiva /health/-päätepiste, määritä ALB:n health check ja luo 5xx-hälytys sekä sähköpostitilaus SNS:ään.
  7. Automatisoitu julkaisu: yhdistä GitHub Actions IAM-rooliin OIDC:llä, rajaa luottamus omaan repositorioon ja main-haaraan, julkaise image commit-SHA:lla ja päivitä ECS task definition.
  8. Siivous: tallenna tarvittavat havainnot, tarkista laskutus ja poista harjoituksen resurssit terraform destroy-komennolla. Huomaa, että erikseen säilytettäväksi jätetty state-bucket ei välttämättä poistu samalla.

Mistä tiedät, että harjoitus onnistui?

  • Sovellukseen pääsee ALB:n DNS-nimen kautta ja health check näyttää kohteet terveiksi.
  • Sovellus yhdistää RDS:ään ilman, että tietokanta on julkisesti saavutettavissa.
  • Kontin lokit näkyvät CloudWatch Logsissa ja virhehälytys voidaan testata.
  • GitHubin main-haaraan tehty muutos rakentaa uuden image-version ja päivittää ECS-palvelun.
  • Terraformin state on tallessa etäbackendissa, eikä salaisuuksia ole commitoitu repositorioon.
