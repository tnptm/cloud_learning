Terraform – syntaksi ja komentojen opetusmateriaali

Opi määrittelemään, suunnittelemaan ja hallitsemaan infrastruktuuria koodilla. Materiaali kattaa HCL-kielen perusteet, Terraformin keskeiset lohkot, komentorivityökalut sekä käytännön DevOps-työnkulun.

1. Terraformin toimintaperiaate

Terraform on HashiCorpin kehittämä Infrastructure as Code (IaC) -työkalu, jolla infrastruktuuria määritellään, hallitaan ja ylläpidetään ohjelmallisesti.

Sen avulla voidaan esimerkiksi luoda virtuaalikoneita, verkkoja, tietokantoja, palomuureja ja muita pilvipalveluiden resursseja. Terraform perustuu deklaratiiviseen toimintamalliin: kehittäjä määrittelee halutun lopputuloksen eikä kaikkia yksittäisiä vaiheita, joilla siihen päästään.

1. ConfigurationKirjoitetaan .tf-tiedostot
2. PlanSuunnitellaan tarvittavat muutokset
3. ApplyToteutetaan muutokset
4. StateTallennetaan resurssien tila

Terraform vertaa määriteltyä tavoitetilaa nykyiseen tilaan ja muodostaa suunnitelman tarvittavista muutoksista. Se ei ole sidottu yhteen pilvipalveluun: sitä voidaan käyttää esimerkiksi AWS:n, Azuren, Google Cloudin ja paikallisten resurssien hallintaan.

2. Asennus ja projektirakenne

Terraformia käytetään komentoriviltä. Asennuksen jälkeen tarkista ohjelman versio:

terraform version

Tyypillinen Terraform-projekti voi sisältää seuraavat tiedostot:

terraform-project/
├── main.tf
├── variables.tf
├── outputs.tf
├── providers.tf
├── terraform.tfvars
└── .terraform.lock.hcl

outputs.tfTulostettavat arvot.

Hyvä tietääTerraform lukee automaattisesti nykyisen hakemiston kaikki .tf- ja .tf.json-tiedostot. Tiedostojen jakaminen on projektin organisointia varten, ei tekninen vaatimus.

3. HCL – HashiCorp Configuration Language

Terraform käyttää määrityskieltä nimeltä HCL. Sen syntaksi on helposti luettavaa ja muistuttaa rakenteeltaan JSONia.

3.1 Kommentit

# Yhden rivin kommentti
// Myös tämä on yhden rivin kommentti

/*
  Monirivinen kommentti.
  Voidaan käyttää pidempiin selityksiin.
*/

# String
name = "web-server"

# Number
instance_count = 2

# Boolean
enabled = true

# List
availability_zones = ["eu-north-1a", "eu-north-1b"]

# Map
tags = {
  Environment = "development"
  Owner       = "devops"

3.3 Lohkot (Blocks)

Terraformin määritykset koostuvat lohkoista. Yleinen rakenne:

block_type "label1" "label2" {
  argument = value
}

Esimerkki resurssilohkosta:

resource "aws_instance" "web" {
  ami           = "ami-12345678"
  instance_type = "t3.micro"
}
  • resource määrittää lohkotyypin.
  • aws_instance kertoo resurssin tyypin.
  • web on resurssin paikallinen nimi.

3.4 String-interpolaatio

Muuttujien ja muiden arvojen sisällyttäminen merkkijonoon tapahtuu ${}-syntaksilla.

variable "environment" {
  default = "development"
}

resource "example_resource" "app" {
  name = "application-${var.environment}"
}

3.5 Funktiot

Terraform sisältää valmiita funktioita merkkijonojen, listojen, numeroiden ja muiden arvojen käsittelyyn.

upper("terraform")
lower("TERRAFORM")
length(["one", "two", "three"])
join("-", ["web", "server", "01"])
element(["a", "b", "c"], 0)
replace("hello-world", "-", "_")

4. Terraformin tärkeimmät lohkotyypit

4.1 Provider – palveluntarjoaja

Provider on lisäosa, jonka avulla Terraform kommunikoi ulkoisen palvelun tai järjestelmän kanssa.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "eu-north-1"
}
  • required_providers määrittelee tarvittavat providerit.
  • source kertoo providerin lähteen Terraform Registryssä.
  • version määrittelee sallitun version.
  • region kertoo AWS-alueen.
TunnistautuminenProviderin tunnistautuminen kannattaa toteuttaa ympäristömuuttujilla tai pilvipalvelun omalla tunnistautumismekanismilla. Älä kirjoita salasanoja tai pääsyavaimia Terraform-tiedostoihin.

4.2 Resource – resurssin määrittely

resource on Terraformin keskeisin lohkotyyppi. Sen avulla luodaan ja hallitaan infrastruktuurin resursseja.

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  tags = {
    Name        = "web-server"
    Environment = "development"
  }
}

Resurssin yleinen syntaksi on resource "PROVIDER_RESOURCE_TYPE" "LOCAL_NAME". Resurssiin viitataan esimerkiksi muodossa aws_instance.web ja sen ominaisuuteen muodossa aws_instance.web.instance_type.

4.3 Variable – muuttujat

Muuttujilla tehdään määrityksistä uudelleenkäytettäviä.

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t3.micro"
}

variable "environment" {
  description = "Deployment environment"
  type        = string
  default     = "development"
}

variable "instance_count" {
  description = "Number of instances"
  type        = number
  default     = 1
}

Muuttujaa käytetään var.-etuliitteellä:

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = var.instance_type

  tags = {
    Environment = var.environment
  }
}

Arvoja voidaan antaa oletusarvolla, komentoriviltä, muuttujatiedostosta tai ympäristömuuttujasta.

# Komentoriviltä
terraform apply -var="environment=production"

# terraform.tfvars
# environment    = "production"
# instance_type  = "t3.small"
# instance_count = 2

# Ympäristömuuttujasta
export TF_VAR_environment="production"

Terraform lataa automaattisesti nykyisen hakemiston terraform.tfvars-tiedoston. Ympäristömuuttujat tunnistetaan TF_VAR_-etuliitteestä.

4.4 Locals – paikalliset arvot

locals-lohkoa käytetään laskettujen tai useissa paikoissa tarvittavien arvojen määrittelyyn.

locals {
  project_name = "my-application"
  environment  = "development"

  common_tags = {
    Project     = local.project_name
    Environment = local.environment
    ManagedBy   = "Terraform"
  }
}

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"
  tags          = local.common_tags
}

4.5 Output – tulosteet

output-lohkon avulla näytetään Terraformin hallinnoimien resurssien tietoja.

output "instance_id" {
  description = "EC2 instance ID"
  value       = aws_instance.web.id
}

output "instance_public_ip" {
  description = "Public IP address"
  value       = aws_instance.web.public_ip
}

Tulosteita voi tarkastella komennoilla terraform output, terraform output instance_id ja terraform output -json.

4.6 Data source – olemassa olevan resurssin lukeminen

data-lohko hakee tietoja olemassa olevasta resurssista luomatta kyseistä resurssia.

data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"
}

resource luo tai hallitsee resurssia, kun taas data hakee tietoa jo olemassa olevasta resurssista.

4.7 Terraform-lohko

terraform-lohko sisältää Terraformin toimintaan ja riippuvuuksiin liittyviä asetuksia.

terraform {
  required_version = ">= 1.10.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

4.8 Provisioner – komentojen suorittaminen

Provisioner mahdollistaa komentojen suorittamisen resurssin luonnin tai poistamisen yhteydessä.

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  provisioner "local-exec" {
    command = "echo Instance created"
  }
}

Provisionereita ovat local-exec (komento Terraformia ajavassa ympäristössä), remote-exec (komento etäkoneessa) ja file (tiedostojen kopiointi etäkoneeseen).

SuositusProvisionereiden käyttöä kannattaa yleensä välttää, jos sama asia voidaan toteuttaa pilvipalvelun omilla mekanismeilla, cloud-initillä tai konfiguraationhallintatyökaluilla.

5. Ehtolauseet ja silmukat

5.1 Conditional expression – ehtolause

Ehtolauseen syntaksi on condition ? true_value : false_value.

variable "environment" {
  type    = string
  default = "development"
}

locals {
  instance_type = var.environment == "production" ? "t3.medium" : "t3.micro"
}

Jos ympäristö on production, käytetään suurempaa instanssia. Muussa tapauksessa käytetään pienempää.

locals {
  is_production  = var.environment == "production"
  is_development = var.environment == "development"
  enable_monitoring = local.is_production || local.is_development
}

5.2 count – resurssien määrän määrittely

count mahdollistaa useamman samanlaisen resurssin luomisen.

variable "instance_count" {
  type    = number
  default = 2
}

resource "aws_instance" "web" {
  count         = var.instance_count
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-${count.index}"
  }
}

Jos instance_count on 2, Terraform luo kaksi instanssia. Viittaukset tehdään indeksillä, esimerkiksi aws_instance.web[0].id. count.index alkaa nollasta.

5.3 for_each – resurssien luominen kokoelman perusteella

variable "servers" {
  type = map(string)
  default = {
    web = "t3.micro"
    api = "t3.small"
    db  = "t3.medium"
  }
}

resource "aws_instance" "server" {
  for_each      = var.servers
  ami           = "ami-0123456789abcdef0"
  instance_type = each.value

  tags = {
    Name = each.key
  }
}

each.key tarkoittaa avainta ja each.value sen arvoa. Resursseihin viitataan esimerkiksi muodossa aws_instance.server["web"].id.

for_each on usein parempi vaihtoehto, jos resursseilla on omat nimet ja ominaisuudet.

5.4 for – kokoelman käsittely

variable "names" {
  default = ["web", "api", "database"]
}

locals {
  upper_names = [
    for name in var.names : upper(name)
  ]
}

Tuloksena on lista ["WEB", "API", "DATABASE"]. Map-rakenne voidaan muodostaa esimerkiksi näin:

locals {
  server_map = {
    for name in var.names : name => "server-${name}"
  }
}

5.5 Dynamic blocks – dynaamiset lohkot

dynamic mahdollistaa sisäkkäisten lohkojen luomisen kokoelman perusteella.

variable "allowed_ports" {
  default = [80, 443]
}

resource "aws_security_group" "web" {
  name = "web-security-group"

  dynamic "ingress" {
    for_each = var.allowed_ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["192.0.2.0/24"]
    }
  }
}

Esimerkissä muodostetaan kaksi ingress-sääntöä. Dynaamiset lohkot ovat hyödyllisiä, kun resurssin sisällä tarvitaan vaihteleva määrä sisäkkäisiä lohkoja.

6. Resurssien riippuvuudet

Terraform muodostaa automaattisesti riippuvuusgraafin. Jos resurssi käyttää toisen resurssin arvoa, Terraform ymmärtää niiden välisen riippuvuuden.

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

Terraform tietää, että subnet voidaan luoda vasta VPC:n luonnin jälkeen.

depends_on

Jos riippuvuutta ei voi ilmaista suoraan resurssiviittauksella, voidaan käyttää depends_on-määritystä.

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  depends_on = [aws_vpc.main]
}

depends_on kannattaa jättää käyttämättä silloin, kun riippuvuus voidaan ilmaista selkeämmin suoran resurssiviittauksen avulla.

7. Lifecycle – resurssin elinkaaren hallinta

lifecycle-lohko sisältää asetuksia, joilla voidaan vaikuttaa resurssien luontiin, päivittämiseen ja poistamiseen.

create_before_destroy

Luo uuden resurssin ennen vanhan poistamista.

lifecycle {
  create_before_destroy = true
}

prevent_destroy

Estää resurssin poistamisen Terraformin kautta, kun asetus on mukana konfiguraatiossa.

lifecycle {
  prevent_destroy = true
}

ignore_changes

Määrittelee ominaisuudet, joiden muutoksia Terraform ei huomioi suunnitelmaa tehdessään.

lifecycle {
  ignore_changes = [tags]
}
Muistaprevent_destroy ei ole varmuuskopio eikä suojaa resurssia kaikilta poistotavoilta. ignore_changes voi puolestaan peittää konfiguraation ja todellisen tilan välisiä eroja, joten käytä sitä harkiten.

8. Moduulit – Terraform-koodin uudelleenkäyttö

Moduuli on kokoelma Terraform-tiedostoja, joilla toteutetaan tietty kokonaisuus. Esimerkiksi verkkoinfrastruktuuri voidaan toteuttaa omana moduulina.

terraform-project/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
    └── network/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf

Moduulin sisältö

modules/network/main.tf

resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr
  tags = {
    Name = var.vpc_name
  }
}

modules/network/variables.tf

variable "vpc_cidr" {
  type = string
}

variable "vpc_name" {
  type = string
}

modules/network/outputs.tf

output "vpc_id" {
  value = aws_vpc.main.id
}

Moduulin käyttäminen

Juuritason main.tf:

module "network" {
  source   = "./modules/network"
  vpc_cidr = "10.0.0.0/16"
  vpc_name = "development-vpc"
}

Moduulin output-arvoon päästään käsiksi muodossa module.network.vpc_id.

  • Koodi voidaan käyttää uudelleen.
  • Projektin rakenne selkeytyy.
  • Infrastruktuuri voidaan jakaa loogisiin osiin.
  • Toteutukset pysyvät yhtenäisempinä eri ympäristöissä.

9. Terraform State – infrastruktuurin tilanhallinta

Terraform ylläpitää state-tiedostoa, jossa kuvataan Terraformin hallinnoimien resurssien tila ja yhteydet todellisiin infrastruktuuriresursseihin.

Oletusarvoisesti state tallennetaan paikalliseen tiedostoon terraform.tfstate. Se on tärkeä osa Terraformin toimintaa: sen avulla Terraform yhdistää konfiguraation resurssit jo hallinnassa oleviin resursseihin.

State-komennot

# Näytä hallinnoidut resurssit
terraform state list

# Näytä yksittäisen resurssin tiedot
terraform state show aws_instance.web

# Siirrä resurssin osoite state-tiedostossa
terraform state mv aws_instance.web aws_instance.application

# Poista resurssin hallintatieto statesta
terraform state rm aws_instance.web
Huomaaterraform state rm ei poista varsinaista pilviresurssia. Se poistaa vain Terraformin hallintatiedon.

Remote state – etätilanhallinta

Tiimityöskentelyssä state-tiedosto kannattaa yleensä tallentaa keskitettyyn backend-palveluun, esimerkiksi AWS S3:een tai Azure Storageen.

terraform {
  backend "s3" {
    bucket       = "my-terraform-state"
    key          = "development/terraform.tfstate"
    region       = "eu-north-1"
    use_lockfile = true
  }
}

S3-bucketin on oltava olemassa ennen backendin käyttöönottoa. Remote staten etuja ovat yhteinen tila, keskitetty hallinta ja mahdollisuus lukita tila samanaikaisten muutosten ajaksi.

TietoturvaState-tiedosto voi sisältää salasanoja, tunnisteita ja muita arkaluonteisia arvoja. Suojaa sen tallennuspaikka ja käyttöoikeudet huolellisesti.

10.3 terraform validate

terraform validate

Tarkistaa syntaksin ja konfiguraation sisäisen rakenteen. Se ei varmista, että resurssin asetukset toimivat oikeassa pilviympäristössä, eikä toteuta muutoksia.

10.4 terraform plan

# Näytä suunnitellut muutokset
terraform plan

terraform plan -out=tfplan

# Tarkastele tallennettua suunnitelmaa
terraform show tfplan

Tallennetun suunnitelman voi toteuttaa komennolla terraform apply tfplan. Plan on tärkeä, koska sen avulla muutokset voidaan tarkastaa ennen infrastruktuurin muokkaamista.

10.5 terraform apply

# Näytä suunnitelma ja pyydä hyväksyntä
terraform apply

# Hyväksy automaattisesti
terraform apply -auto-approve

Automaattista hyväksyntää kannattaa käyttää vain, kun hyväksyntäprosessi on muuten toteutettu luotettavasti, esimerkiksi CI/CD-putkessa.

terraform destroy

# Hyväksy poistaminen automaattisesti
terraform destroy -auto-approve

10.9 terraform import

Import mahdollistaa olemassa olevan resurssin ottamisen Terraformin hallintaan.

terraform import aws_instance.web i-0123456789abcdef0

Import ei yleensä kirjoita resurssin Terraform-konfiguraatiota automaattisesti. Resurssille täytyy laatia vastaava resource-määritys.

Uudemmassa Terraformissa voidaan käyttää myös deklaratiivista import-lohkoa:

import {
  to = aws_instance.web
  id = "i-0123456789abcdef0"
}

Tämän jälkeen käytetään normaalia plan- ja apply-työnkulkua.

11. Terraformin komentojen käytännön työnkulku

Tavallinen Terraform-kehitystyö noudattaa seuraavaa järjestystä:

  1. Luo projektihakemisto.
    mkdir terraform-project
cd terraform-project
  2. Kirjoita Terraform-määritykset. Luo esimerkiksi main.tf, variables.tf ja outputs.tf.
  3. Alusta projekti.
    terraform init
  4. Muotoile ja tarkista.
    terraform fmt -recursive
terraform validate
  5. Tarkasta suunnitelma.
    terraform plan
  6. Toteuta muutokset.
    terraform apply
  7. Tarkastele lopputulosta.
    terraform output
terraform state list
  8. Poista harjoitusympäristö tarvittaessa.
    terraform destroy

Tämä työnkulku on hyvä perusta myös automatisoiduille CI/CD-prosesseille.

12. Ympäristöt ja Workspaces

Terraform Workspaces mahdollistaa useamman erillisen state-tilan käyttämisen saman konfiguraation yhteydessä. Esimerkiksi kehitys- ja tuotantoympäristöille voidaan käyttää eri työtiloja.

# Listaa työtilat
terraform workspace list

# Luo uusi työtila
terraform workspace new development

# Vaihda työtilaa
terraform workspace select production

# Näytä aktiivinen työtila
terraform workspace show

# Poista työtila
terraform workspace delete development

Työtilaa voidaan hyödyntää ympäristökohtaisten asetusten valintaan:

locals {
  instance_type = terraform.workspace == "production" ? "t3.medium" : "t3.micro"
}

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = local.instance_type
}
HuomioWorkspaces ei itsessään eristä pilviympäristöjä tai käyttöoikeuksia. Suuremmissa järjestelmissä erilliset Terraform-projektit ja backendit voivat olla selkeämpi ja turvallisempi ratkaisu.

14. Terraform ja Git-versionhallinta

Terraform-projektit kannattaa tallentaa Git-repositorioon. Kaikkia Terraformin luomia tiedostoja ei kuitenkaan pidä lisätä versionhallintaan.

# .gitignore

# Terraform working directory
.terraform/

# Terraform state files
*.tfstate
*.tfstate.*

# Crash logs
crash.log
crash.*.log

# Variable files containing sensitive values
*.tfvars
*.tfvars.json

# Override files
override.tf
override.tf.json
*_override.tf
*_override.tf.json

# Saved plan files
*.tfplan

# Local CLI configuration
.terraformrc
terraform.rc
  • .terraform.lock.hcl kuuluu yleensä versionhallintaan.
  • *.tfstate ei kuulu Git-repositorioon.
  • Salaisuuksia sisältäviä muuttujatiedostoja ei pidä tallentaa julkiseen repositorioon.
  • Terraform-koodin tulee olla versionhallinnassa, jotta infrastruktuurin muutokset voidaan jäljittää.

15. Terraform CI/CD-putkessa

Terraform soveltuu hyvin automatisoituun infrastruktuurin hallintaan esimerkiksi GitHub Actionsin avulla.

DeveloperMuuttaa Terraform-koodia
Pull RequestKoodin katselmointi
Terraform CIfmt, validate, plan
Approval & ApplyHyväksyntä ja käyttöönotto

Esimerkki GitHub Actions -workflowsta:

name: Terraform CI

on:
  pull_request:
    paths:
      - 'terraform/**'
  push:
    branches:
      - main
    paths:
      - 'terraform/**'

jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3

      - name: Terraform Init
        run: terraform init -input=false

      - name: Terraform Format
        run: terraform fmt -check -recursive

      - name: Terraform Validate
        run: terraform validate

      - name: Terraform Plan
        run: terraform plan -input=false

Tämä on CI-esimerkki, joka tarkistaa konfiguraation ja muodostaa suunnitelman. Varsinainen tuotantokäyttöönotto kannattaa toteuttaa erillisellä hyväksytyllä Apply-vaiheella.

Tuotantokäytössä huomioi pilvipalvelun tunnistautuminen, remote state ja lukitus, provider-versioiden lukitseminen, Apply-vaiheen käyttöoikeudet sekä suunnitelman hyväksyntä.
